[ASSISTANT] Your login, registration, database access and ownership checks have to stay in PHP. The best candidates for JS are the interactions that currently reload the whole page.



## Good candidates



1. **Toggling a task done** (`toggle_task.php`, the checkbox with `onchange="this.form.submit()"`). This is the best first conversion. Checking a box reloads the page and loses your scroll position. With JS you'd `fetch` a POST, then update the row's `todo-item--done` class and the counts. PHP would still do the DB update, but it would return JSON or a status code instead of redirecting.



2. **Deleting a task** (`delete_task.php`, the `confirm()` link). Right now it's a GET link that changes data, which isn't safe because a prefetch or a pasted link can delete tasks. JS lets you send a `DELETE` or POST with `fetch` and remove the `<li>` from the page.



3. **The "Add New Task" form** (`tasks.php?action=add`). Opening the form currently reloads the page with a query string. JS could show or hide the partial instead. You could also submit it with `fetch` and add the new row without reloading.



4. **Client-side form validation** (`create_task.html.twig`, the login and register forms). Checks like required fields and date format would give instant feedback. This only adds convenience. Keep the PHP validation in `save_task.php`, because users can bypass JS.



5. **Filter tabs** (`tasks.php?status=`). This is lower priority. Each tab is a full page load, which works fine. You could filter the already-loaded list in JS, but then the counts and the filtering logic exist in two places.



## Keep in PHP



- **Authentication and sessions**: `login_process.php`, `register_process.php` and `logout.php`. Anything that handles passwords or trust belongs on the server.

- **Authorization**: every `user_id` check comes from the session. Even with JS, each endpoint must still verify ownership.

- **Initial rendering with Twig**: the first page load should still be server-rendered. That is also what you just converted.

- **Server-side validation and whitelists**: the priority and status whitelists and the date check in `save_task.php`.



## Suggested order



Start with the toggle, because it's the simplest and the most visible improvement. Then do delete, then the add form. Each one follows the same pattern, so you learn it once:



1. Change the PHP endpoint to return JSON (or just an HTTP status) instead of `header('Location: ...')`.

2. Add a `.js` file that listens for the event, calls `fetch`, and updates the DOM.



You'll also need to decide how the page gets updated. If the JS builds new rows itself, the HTML lives in both Twig and JS. If it only flips classes and text on existing rows, that duplication is avoided.
